## 为什么"登录"必须排在"发留言"前面

我原来的计划是「先做一个不用登录的匿名版，再加登录」。**这个计划被现实推翻了**，原因值得记住：

云端数据库有一道铁律 —— **每一行数据都必须有主人**。表结构里 `owner_id` 这个字段是 `NOT NULL`，而且它的值是服务器根据"当前登录的是谁"自动填的。

结果就是：

- **没登录** → 不知道你是谁 → `owner_id` 填不出来 → **写入被拒绝**
- 登录了 → 服务器知道你是谁 → 自动填上 → 写入成功

所以不是"想不想加登录"的问题，**是这台数据库不接受没有身份的人写数据**。

> 一句话：**「你是谁」在云端是一个必需品，不是一个可选项。**

## 怎么跑

**这个项目不能用双击打开。**

云服务除了一般的登录校验，还有一道额外的门：**它只认自己那个域名的网页。** 网页从哪个域名打开的，它就要求是那个域名，别的地址一律拒绝。

- 本地双击打开 → 页面地址是 `file://…` → 云端拒绝 ❌
- 从公网地址打开 → 地址对得上 → 云端放行 ✅

这是**故意的安全设计**：防止别人把你的网页整个拷走、挂到自己的域名下白用你的后端。

所以运行方式是：**发布到公网，然后用公网地址打开。** 页面顶部有一条提示条，会把"当前地址"和"要求的地址"都显示出来 —— 以后读不到数据，先看这一行。

**登录功能也一样，只能在发布后的正式地址上用。** 预览地址和 localhost 都调不通登录 —— 因为云端没给它们登记过。

## 数据库

云端的表叫 `messages`：

| 字段 | 类型 | 说明 |
|---|---|---|
| `id` | BIGINT | 主键，自动递增。每一行的唯一编号 |
| `owner_id` | TEXT | **主人是谁**。默认值 `auth.uid()`，由服务器自动填，前端不许传 |
| `owner_name` | TEXT | 展示用的昵称（只为好看，不参与权限判断） |
| `content` | TEXT | 留言内容 |
| `created_at` | TIMESTAMPTZ | 写入时间，服务器自动填 |

**三道门（RLS 行级安全）**：

| 策略 | 管什么 | 规则 |
|---|---|---|
| `messages_read_all` | 谁能读 | **所有人**（含未登录） |
| `messages_insert_own` | 谁能写 | 只有登录的人，且只能以自己的身份写 |
| `messages_delete_own` | 谁能删 | 只有本人能删自己的 |

权限判断发生在**数据库那一层**，不在网页里。也就是说，就算有人把网页代码改掉、硬要删别人的留言，数据库也会拒绝。**网页只是"面子"，数据库才是"里子"。**

## 登录是怎么设计的（第 2 步）

云端允许的登录方式有三种，**每一种都必须经过邮箱验证码**：

| 方式 | 流程 | 用到的接口 |
|---|---|---|
| 密码登录 | 邮箱 + 密码 → 直接进 | `signInWithPassword` |
| 验证码登录 | 邮箱 → 收码 → 填码进 | `signInWithOtp` → `verify` |
| 注册 | 邮箱 → 收码 → 填码 **+ 设密码** → 建号并登录 | `sendOtp` → `verifyOtp` |

另外还有一个**重置密码**（从"密码登录"页的「忘记密码？」进去）：
邮箱 → 收码 → 填码 + 新密码 → 重设并自动登录。

**几条要记住的规矩**：

- **注册不能跳过邮箱验证。** 云端不提供"邮箱 + 密码直接注册"这条捷径 —— 必须先证明邮箱是你的，才能建账号。这也是为什么注册也要收验证码。
- **登录失败时故意只说"邮箱或密码不对"**，不区分"这个邮箱没注册过"。否则别人就能拿它来试探哪些邮箱是这里的用户。
- **匿名登录是故意不开放**的。它和"每行数据都要有主人"这条铁律直接冲突，所以云端干脆没提供。**遇到读不到数据时，正确做法是去登录，而不是找个假身份绕过。**
- 退出后再登录不用刷新页面 —— 页面订阅了登录状态的变化。

### 一个关键区别：问 vs 通知

```js
// 问：我主动去问云端"现在登录着吗"
await cloud.auth.getSession()

// 通知：我不问，云端那边一变就主动告诉我
cloud.auth.onAuthStateChange((event, session) => { ... })
```

登录、退出、通行证过期，都会触发后面那种通知。**页面不用反复去问，等着被通知就行。**

## 发留言是怎么设计的（第 3 步）

**写和读只差一个动作：**

```js
// 读
cloud.database.from('messages').select('id, owner_name, content, created_at')

// 写
cloud.database.from('messages').insert({ content: '…', owner_name: '…' }).select()
```

`.insert()` 后面那个 **`.select()` 不是装饰** —— 它让云端把"刚写进去的那一行"回传给我。这样我们才知道服务器给它分配了**什么编号、什么时间**（这两个值都是服务器填的，前端给不了）。

### ⚠️ 一条必须记住的规矩：前端不许传 `owner_id`

`owner_id` 的值是服务器看"现在登录的是谁"自己填的（`DEFAULT auth.uid()`）。

- **不传** → 服务器自动填 = 正确 ✅
- **传一个空值（`null`）** → 会**覆盖掉**那个默认值 → 被数据库拒掉 ❌
- **传别人的 id** → 被 RLS 那道门拒掉 ❌

一句话：**前端只负责说"写什么"，"算谁的"由数据库自己决定。** 换台电脑、改掉网页代码也绕不过去，因为判断发生在数据库那一层。

前端能传的只有两样：

| 传什么 | 作用 |
|---|---|
| `content` | 留言内容 |
| `owner_name` | 展示用的昵称（只为好看，**不参与任何权限判断**） |

### 为什么发完要"重新读一遍"，而不是直接把新留言插到列表最前面？

那样看起来更流畅，但会掩盖真相 —— **"我们以为写成功了"和"云端真的有了"是两件事**。

所以发完统一做一件事：**重新去云端读一遍列表**。写进去不算数，**读回来才算数**。这也正好让"读"和"写"两条链路互相验证。

### 万一「发表」或「删除」失败，怎么查（排查手册）

**第一步永远是：看那行小字。** 它会告诉你流程走到哪一步断的：

| 页面上显示 | 卡在哪 | 怎么办 |
|---|---|---|
| `① 正在确认登录状态…` | 停在"查登录状态" | Console 里会有 `[开门检查]…`，多半是登录凭据过期 → 重新登录 |
| `这一步需要先登录…` | **没登录**（这不是 bug，是设计） | 登录之后再操作 |
| `先写点内容。` | 内容框是空的 | 写上字再点 |
| `② 正在写入云端…（最多等 15 秒）` | 请求已发出，等云端回 | 超过 15 秒会变成"等了 15 秒服务器还没回应" |
| `云端拒绝了这次写入：…` | 被服务器那道 RLS 门拦住 | 说明这次请求没带上你的身份 → 退出重登再试 |
| `⚠️ 一行都没删掉…` | **被 RLS 拦住了**（这是第 4 步的正常结果，不是 bug） | 那条留言不归你。看一眼它还在不在 |
| `写入失败：…` / `删除失败：…` | 服务器返回了别的错误 | 把那句原文发出来 |
| `出错：…（细节已打到 Console）` | **代码自己抛错了**（不是服务器的错） | 按 F12 → Console，把红字发出来 |
| `③ 已写入（编号 XX）…` / `③ 已删掉…` | 成功 | — |

**为什么代码里要写这么多"啰嗦"的提示？**

因为最坏的失败不是"报错"，而是**什么都不说**。浏览器有个默认行为：代码抛出的错误如果没人接住，它会**悄悄吃掉** —— 页面看着一切正常，功能其实已经断了。这种"静默失败"是最难查的一类 bug。

所以这几个版本都做了三件事：

1. 整个流程套进 `try / catch`（出错必定显示出来）
2. 每个请求配一个 **15 秒闹钟**（不会永远停在"正在处理…"这种既不算成功也不算失败的状态）
3. 装了**两个全局兜底**（任何没被接住的错误，都会在页面状态行里露头，并在 Console 留下原文）

这三件事和"写进去不算数，读回来才算数"是同一条原则：

> **不要让系统的真实状态变成一个谜。**

## 删留言是怎么设计的（第 4 步）

写法上只多了一个链：

```js
// 读
cloud.database.from('messages').select('id, owner_name, content, created_at')

// 写
cloud.database.from('messages').insert({ content: '…', owner_name: '…' }).select()

// 删
cloud.database.from('messages').delete().eq('id', 42).select()
```

### ⭐ 这一版最值钱的一句话：空数组 = 被拦住了，不是成功了

删别人的留言时，云端**不会报错**，也不会提示"你没权限"。它就返回一个**空数组** —— 因为 RLS（行级安全）会把"你不该碰的行"直接过滤掉，连一个错误都不给你。

所以判据不是"有没有 `error`"，而是**删掉了几条**：

```js
const n = Array.isArray(removed) ? removed.length : 0
if (n === 0) {
  // 不是成功。是被拦了，或者这行本来就不在。
}
```

| 情况 | `error` | `data` |
|---|---|---|
| 删成功 | 无 | 被删掉的那一行（长度 1） |
| **删别人的（被 RLS 拦）** | **无** | **`[]` 空数组** |
| 没登录 / 权限被拒 | 有（`42501`） | — |

**中间那一行就是最容易骗人的地方**：不报错、不提示，但什么都没发生。你要是只检查"有没有报错"，就会以为删成功了。

> 这就是「沉默的失败」。它的近亲还有两个：请求发出去了但回程断了（你以为失败、其实成功），服务器答应了却一行没动（你以为成功、其实没动）。
> **共同点：系统的回答 ≠ 系统的真实状态。** 所以任何破坏性操作之后，都要"读回来"再确认一次。

### ⚠️ 另一条铁律：永远不要写"没有条件"的删除

```js
cloud.database.from('messages').delete()          // ❌ 绝对不行
cloud.database.from('messages').delete().eq('id', 42)  // ✅ 永远带上"删哪一条"
```

第一行不是"删错了"，是**一条指令把整张表清空** —— 所有人的留言一起没。这不是比喻。所以规矩是：**`.delete()` 后面必须紧跟一个条件。**

### 为什么「删除」按钮放在每一条留言上，而不只放在自己那条上？

因为**前端判断"这条归不归我"是假的**。

- 前端把按钮藏起来，只让界面好看；改一行代码就绕过去了，它拦不住任何人
- 真正拦人的是数据库那道门（`messages_delete_own` 策略）

所以这一版故意把按钮放在**所有**留言上，当成一次能亲手做的实验：点别人那条「删除」→ 页面会告诉你"一行都没删掉"，而 Console 里**没有任何报错**。眼见为实，比听我说一百遍都管用。

### 二次确认为什么不用浏览器弹窗？

删除是**破坏性操作**，按错了东西就没了，所以需要"上膛 + 开火"两步：

- 第一次点 → 按钮变成实心红的「**真的删？**」（4 秒不点就自动收回，免得你以为它是个普通按钮）
- 第二次点 → 才真的删

**没有用浏览器自带的 `confirm()` 弹窗**，因为那种弹窗在某些嵌入环境下会被直接挡掉，表现就是"点了没反应" —— 正是我们上一次踩过的那个坑。**凡是"可能被环境悄悄挡掉"的东西，都不要拿来当关键步骤。**

| 5 | 点**别人的**留言的「删除」，连点两下 | 状态行出现 ⚠️ **「一行都没删掉」**，而**那条留言还在** |

**第 5 条是这个项目最重要的一次实验。** 顺便按 F12 看 Console：

| Console 里 | 说明 |
|---|---|
| `[第4步-②] 云端回应：{data: [], error: null}` | **没有 error，但 data 是空的** —— 这就是"被拦住了"的样子 |
| 没有红字 | 云端拒绝你的方式是**沉默**，不是报错 |

**再试一次"没登录能不能删"**：

| 该看到的 | 说明 |
|---|---|
| 点「退出」→ 随便点一条留言的「删除」 | |
| 页面自动打开登录框，提示「这一步需要先登录」 | 跟发留言用的是同一个**开门检查** |

> **一句话总结第 4 步**：安全不写在页面上，写在数据库里。页面只是"面子"，数据库才是"里子"。

## 自动化检查是怎么做的（项目 5）

在这之前，"检查代码对不对"全是**手动**的：改完跑一遍自检脚本、盯着 Console 看有没有红字。手动做的事，人一懒就漏。

现在加了自动化：**文件放在 `.github/workflows/check.yml`，GitHub 就会在有人往 main 推代码时，自己开一台机器把它们跑一遍。**

### 三个概念

| 概念 | 在文件里的位置 | 意思 |
|---|---|---|
| **触发** | `on:` | 什么时候跑。这里写的是"往 main 推代码时"，另外加了 `workflow_dispatch` 让你能手动点一下 |
| **机器** | `runs-on:` | 借哪台机器跑。`ubuntu-latest` 是 GitHub 免费提供的，**每次都是全新的，跑完整台扔掉** |
| **步骤** | `steps:` | 跑什么。一步一件事，按顺序做，**任何一步失败，后面就不跑了** |

### 一个容易搞混的点

这个文件**不是**在你电脑上跑的，也**不需要**你开着电脑 —— 它跑在 GitHub 那边。

所以它会看到的东西，就是你**推上去的那份代码**。你在本地改了但没推，它看不到。

### 现在每次推代码，机器自动做 6 件事

```
① 把代码取下来        ② 装 Node（22）        ③ 报一下环境
④ node --check 语法检查
⑤ 跑自检 scripts/check.mjs    ← 52 项
⑥ 收工
```

**第 ⑤ 步才是自动化真正的价值。** 在这之前，那 52 项检查靠人记着做 —— 而"靠人记着"等于"迟早会漏"。现在它在仓库里，谁推代码都跑。

自检脚本住在 `scripts/check.mjs`：可以本地跑（`node scripts/check.mjs`），也可以被机器跑。**同一份脚本，两个地方用。**

### ⚠️ 两个踩过的坑

**坑 1：两种"Node 版本"是两回事 —— 这里我判断错过一次。**

`check.yml` 里有两个跟 Node 有关的写法，含义完全不同：

| 写法 | 管什么 | 谁说了算 |
|---|---|---|
| `node-version: '22'` | **给我们的项目**装哪个 Node | 我们自己写 |
| `uses: actions/checkout@v5` | **这个现成步骤自己**用什么 Node 跑 | action 的作者写，我们改不了，只能升版本 |

踩坑经过：运行日志里有一条黄字 `Node.js 20 is deprecated`。我一开始以为是 `node-version` 太低，把它从 `20` 升到 `22` —— **没用，黄字还在**。

查了 action 的源码才明白：`@v4` 版本的 `action.yml` 里写死 `using: node20`，**跟我们的 `node-version` 毫无关系**。`@v5` 起才改成 `node24`。所以修法是升 action 版本：`@v4 → @v5`。改完黄字消失。

**教训**：警告里提到的东西，不一定是它字面上说的那个。**先查证，再动手。**

**坑 2：自检脚本里不能写死路径。**

脚本原来放在仓库外面（我电脑的某个文件夹），里面写死了绝对路径。搬进仓库后必须改成"按脚本自己的位置往上推一层"：

```js
const ROOT = join(dirname(fileURLToPath(import.meta.url)), '..')
```

这样不管在哪台机器、哪个目录跑，都能找对文件。

### 自检脚本为什么用「退出码」说话

脚本最后一句是：

```js
process.exit(fail === 0 ? 0 : 1)
```

**全过 → 退出码 0 → 绿勾；有不过 → 退出码 1 → 红叉。**

这就是机器能替你报警的机制 —— 不然 GitHub 怎么知道该给红还是给绿？

### 密钥扫描为什么要求"长到像真钥匙"才报

如果只要出现 `sk-` 或 `password` 就报警，会满屏误报 —— HTML 里的 `type="password"` 只是输入框属性，根本不是密钥。

所以判据要求**后面跟一长串字符**（`sk-` 后面 16 位以上），只有"长到像真钥匙"的形状才报。**判据太松，报出来没人看；太紧，真出事也不报。**

### 怎么看结果

1. GitHub 仓库页面点顶部的 **Actions**
2. 左边选「自动检查」，右边能看到每次运行的记录
3. **绿色 ✅ = 全过；红色 ❌ = 有一步失败了**，点进去能看到是哪一步、报了什么

提交记录旁边也会带一个小图标（✅ / ❌ / 🟡），一眼就知道那次提交检查过没有。

**还有一个手动入口**：在 Actions 页面选中「自动检查」后，右上角有 **Run workflow** 按钮 —— 不用推代码也能跑一次。这个入口就来自 `on:` 下面那行 `workflow_dispatch:`。

### 后面还能加什么

- 检查失败时**自动通知**（邮件 / 微信）
- 检查过了就**自动部署** —— 那就是 CD

## 每一步都在教同一件事

回头看这几步，其实只讲了一个道理，只是换了四种样子：

| 步骤 | 你可能会以为的"成功" | 真相 | 判断依据 |
|---|---|---|---|
| 1 读 | 页面显示出留言了 | 那可能是本地缓存 | 点「重新读一次」，次数会 +1 |
| 2 登录 | 右上角显示邮箱了 | 刷新一下可能就掉了 | **F5 之后还是登录状态** |
| 3 写 | 提示"发表成功"了 | 请求成功 ≠ 云端存下来了 | **写完重新读一遍** |
| 4 删 | 没报错 | 不报错 ≠ 删掉了 | **看删掉了几条** |

> **不要让系统的真实状态变成一个谜。**
> 别人跟你说"做好了"，你就回一句：**读回来给我看。**
